# Admin V1

## Recuperação e primeira senha

Validação adicional do callback: destino configurado http://localhost:5173/reset-password; GET do callback Neon com código inválido sintético retornou 302 para esse destino com error=INVALID_TOKEN. Páginas abertas por navegação externa simulada retornaram 200 em localhost e 302 no alias numérico. Não foi acessado o link real do titular, portanto a falha original ao abri-lo não foi reproduzida. Foi corrigida a perda de código ao recarregar: a query recebida é convertida em fragmento da URL da aba, que não é enviado em HTTP/referrer nem salvo em localStorage/sessionStorage, e removido após sucesso. Código inválido/ausente/oversized desabilita o formulário. 33 testes passaram; navegador confirmou campos habilitados após reload com código sintético. strictPort impede Vite trocar silenciosamente a porta configurada. O titular deve abrir o e-mail no mesmo computador que mantém o servidor local ativo; localhost em outro dispositivo aponta para esse outro dispositivo.

Correção de origem local: com Allow Localhost habilitado, o Neon desta branch retornou 403 INVALID_REDIRECT_URL quando Origin era http://127.0.0.1:5173, inclusive com redirectTo localhost. Origin e callback ambos localhost retornaram 200 pelo SDK oficial, usando e-mail inexistente (sem envio ao Admin). Login/recuperação/Admin agora redirecionam páginas de aliases numéricos para localhost preservando porta/caminho/query. Nenhum header de Origin é falsificado. A exceção de navegação entre aliases permite somente GET/HEAD de documento, nunca API ou escrita; validação de IP/Host e Origin das escritas continua obrigatória. Erros de recuperação registram somente endpoint, status e código em allowlist; nenhum payload, e-mail, token, senha, cookie ou stack. Não existiam logs persistidos da tentativa original: a falha foi reproduzida diretamente com o SDK. Os testes simulados anteriores não detectavam a restrição de trusted domains do provedor.

O login oferece Esqueci minha senha em /forgot-password. POST /api/auth/request-password-reset consulta somente o e-mail do User ID autorizado e delega ao endpoint oficial request-password-reset; outros e-mails recebem a mesma confirmação genérica sem envio. O redirectTo é fixado no servidor para /reset-password da origem local, nunca recebido do cliente. Não há criação de usuário nem alteração de ID. O Neon Shared entrega o e-mail; somente o titular solicita e abre esse link.

A página /reset-password recebe o token do callback oficial, mantém apenas em memória e remove a query da URL. Referrer-Policy/no-referrer impede propagação a recursos; o servidor do build impede cache dessas páginas. POST /api/auth/reset-password delega token e nova senha ao Neon pelo SDK oficial; o provedor verifica validade, expiração e consumo único. Não persistimos ou imprimimos senha/token, não criamos links ou hashes próprios. Senhas de 8 a 128 caracteres; confirmação na interface. Cadastro continua sem rota pública. Recuperação tem limite de cinco tentativas/minuto por IP e escritas exigem a mesma origem.

Verificação desta etapa: 31 testes locais, build/lint e scan de segredos aprovados. Testes de recuperação usam provedor simulado, sem envio ou alteração de credenciais reais. scripts/check-admin-recovery.mjs confirmou somente por leitura o Admin existente e rejeição de outro e-mail. O envio real e a definição da primeira senha aguardam ação do titular. Nenhuma migration ou alteração dos modelos/botões.

Autenticação gerenciada Neon Auth (Better Auth), integrada pelo SDK oficial @neondatabase/auth/server 0.5.0-beta. O adaptador Node usa handleAuthProxyRequest; não implementa senhas, emissão ou validação própria de tokens.

Configuração privada em .env.server.local: NEON_AUTH_BASE_URL, BIOSITE_ADMIN_AUTH_ID e NEON_AUTH_COOKIE_SECRET (mínimo 32 caracteres, gerado localmente). Nenhum segredo é enviado ao bundle. npm ci usa a configuração legacy-peer-deps para evitar peers de frameworks que este projeto não utiliza.

GET /api/auth/session retorna apenas authenticated. POST /api/auth/login aceita e-mail/senha, valida a sessão emitida junto ao provedor e autoriza exclusivamente o ID configurado. POST /api/auth/logout revoga a sessão no provedor e encaminha a remoção dos cookies. Não há proxy genérico de endpoints do provedor, cadastro, tokens em JSON nem armazenamento de tokens no localStorage.

Todas as demais rotas /api/* exigem sessão validada no servidor antes de acessar o repositório. A autorização consulta get-session com disableCookieCache=true, verifica user.id, session.userId e expiração; cookies falsos, sessão revogada e outras contas não autorizam. Escritas exigem Origin correspondente; sem CORS aberto. Há limite de tentativas de login por IP no processo. O login mobile monta o painel apenas após autenticação; expiração retorna ao login e logout preserva cópias locais de alterações pendentes.

Servidor do build redireciona / e /admin para /login sem sessão. A API permanece protegida independentemente da navegação ou do código frontend. Rotas públicas futuras devem ser implementadas separadamente. Não há storage ou publicação nesta etapa, nem novas migrations.

O servidor continua restrito a loopback. Para deployment posterior serão necessários HTTPS, origem de produção explicitamente configurada, rate limiting compartilhado e role de banco restrita; a role owner atual nunca é usada para autorizar usuários. O SDK utilizado é beta e deve ser acompanhado antes de deployment. Desativar cadastro no painel do provedor quando disponível acrescenta proteção; mesmo outra conta criada diretamente no provedor não acessa este Admin.

Validação: 30 testes locais, build e lint passaram. O teste de autenticação usa provedor simulado e verifica login, ID autorizado, sessão falsa, logout, rotas e dados preservados. O servidor real do build confirmou /admin 302, API sem sessão 401 e login inválido rejeitado pelo Neon com 401. Login real da conta Admin, leitura persistida nessa sessão e logout real ainda dependem de uma entrada do titular na interface; nenhuma senha foi solicitada no chat.

O teste de escrita Neon existente agora exige BIOSITE_TEST_COOKIE fornecido privadamente ao processo, sem bypass de autorização ou impressão do cookie. Não executar sem sessão autorizada. A verificação de fontes confirma os 21 modelos, 14 botões e migration preservados; o build é examinado também quanto ao segredo dos cookies.
